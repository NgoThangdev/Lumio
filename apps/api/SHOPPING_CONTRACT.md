# Shopping Trip API contract

All routes are under `/api/households/:householdId/trips` and require a session and household membership. Item IDs must belong to that household. `GET /:tripId` returns entries with `location: { id, name } | null` and `item: { id, name, primaryUnit, trackingMode, openedTrackingEnabled, preferredRestockLocationId, preferredRestockLocation: { id, name } | null }`. Entry `location` is an explicit quantity-purchase location; item preferred location is the default for future writes. The server-owned `openedTrackingEnabled` boolean tells clients whether a quantity item uses whole-package purchase amounts; it is `false` for items without opened tracking.

## Entries and suggestions

- `POST /` creates a draft trip with `{ store, plannedDate }`.
- `POST /:tripId/entries` adds `{ itemId }` in Draft or Shopping for any tracking mode. A manual entry has `source: "MANUAL"`, `priority: "OPTIONAL"`, and `suggestedQuantity: null`.
- `POST /:tripId/suggestions` imports available recommendations into a draft trip, without changing an existing entry. Quantity items retain their suggested quantity, priority, and reason. FIVE_LEVEL and PRESENCE_BACKUP items assessed as `BUY_BACKUP` get `source: "SUGGESTED"`, assessment priority and reason, and `suggestedQuantity: null`. No backup count is inferred; the shopper enters the actual purchase amount.
- For `QUANTITY` items with `openedTrackingEnabled: true`, both normal and skipped-Optional positive purchase gaps round up to whole containers before import. Their reason states the rounded amount will meet or exceed the target. Ordinary quantity items retain fractional suggestions. Previously imported entry snapshots are unchanged.
- The first import also inspects SKIPPED entries on the single latest `RESTOCKED` trip in the same household whose planned date is no later than the draft's planned date, ordered by completion time then trip ID. This includes entries left Pending at Finish, which Finish marks SKIPPED. MOVED is excluded. Each item is reassessed for the destination planned date: a normal buy keeps its Must/Should priority and amount with `Skipped on the previous trip.` added to its reason; a QUANTITY item without a normal buy recommendation may be Optional for the positive gap between target stock and batches still eligible on that date. Original and opening-based expiry are inclusive on that date. No target or no positive gap adds no skipped recommendation. State items require `BUY_BACKUP`. The lookup does not search older trips when the latest one has no skips, and does not create entries in a selected draft as Move does.
- Import is one-shot once `suggestionsImportedAt` is set, including a zero-entry result. A legacy draft with an existing `SUGGESTED` entry is treated as already imported and gets the marker without recomputing. Existing manual, suggested, and carried MOVED entries keep their source, priority, reason, and quantity snapshot. The unique trip/item key prevents duplicate entries.
- `POST /:tripId/start` starts Shopping.

## Pre-shopping stock check (before first suggestion import)

`GET /:tripId/stock-check` is available to a household member while the trip is `DRAFT` and has no `SUGGESTED` entry. On the first read the server saves a stable, ranked shortlist of at most five household items. Missing five-level/presence state ranks first; otherwise an item with no recorded stock event or one whose latest batch creation, stock action, or prior physical check is at least 30 days old qualifies. Low stock by itself is not an uncertainty signal. The shortlist may include an item that is not currently suggested for purchase. Later reads return the saved shortlist and progress.

Response: `{ tripId, items: [{ itemId, name, trackingMode, openedTrackingEnabled, reason, status, stockRevision, stock, checkedAt, checkedByUserId }] }`. `reason` is `MISSING_STATE`, `NO_STOCK_RECORD`, `STALE_RECORD`, or `STOCK_CHANGED`. `status` is `PENDING`, `CONFIRM`, `CORRECT`, or `STALE`. `stock` is `{ quantity, batches: [{ id, quantity, expiryDate, openedAt, openedUseByDate }] }` for QUANTITY, or `{ currentLevel, isPresent, backupCount }` for state modes. Quantities are decimal strings. The server owns `stockRevision`; any stock-changing action, including Open, Use, Finish opened, Restock, backup and state changes, or a check correction, advances it. A saved confirmation or correction becomes `STALE` when its revision differs from current stock.

`PUT /:tripId/stock-check/:itemId` saves one shortlisted item at a time and returns the same response plus `changed: boolean`. Every request includes `expectedRevision` from GET:

| Decision | Request body beyond `expectedRevision` | Effect |
| --- | --- | --- |
| Confirm | `{ "decision": "CONFIRM" }` | Records actor and time; stock is unchanged. |
| Correct quantity | `{ "decision": "CORRECT", "quantity": "8" }` | Sets observed total. `"0"` is valid. A safe single stock pool is adjusted without losing expiry/opened identity. |
| Correct quantity with batch detail | `{ "decision": "CORRECT", "quantity": "8", "batches": [{ "batchId": "...", "quantity": "3" }], "extraUnopenedQuantity": "1" }` | Required when different expiries or opened identities make a total ambiguous. All positive existing batches must appear; counts may be zero. Extra stock becomes an undated unopened batch. Batch quantities plus extra must equal total. |
| Correct five-level | `{ "decision": "CORRECT", "currentLevel": "HALF", "backupCount": 1 }` | Sets observed current level and backup count. |
| Correct presence/backup | `{ "decision": "CORRECT", "isPresent": true, "backupCount": 1 }` | Sets observed presence and backup count. |

Opened-tracking unopened counts and extra stock must be whole packages; an opened batch cannot exceed one primary unit. Corrections and an append-only actor/time history in the check record commit in one transaction; they never create `USE`, `RESTOCK`, or `ADD_BACKUP` activity. Item detail exposes corrected check records alongside existing activity. Each item saves independently, so leaving and returning to the draft resumes progress. Repeating the same actor's `CONFIRM` at the current revision returns the saved result without adding history. `STOCK_CHANGED` (409) means the submitted revision is stale; reload before confirming or correcting. `BATCH_DETAIL_REQUIRED` (409) means the server cannot safely attribute a total correction; show the batch counts. Other invalid counts or fields return 400. Missing membership returns 403, absent trip/item 404, and a non-draft or already-imported draft returns 409 (`TRIP_NOT_DRAFT` or `SUGGESTIONS_ALREADY_IMPORTED`).

The check's other error messages are `INVALID_EXPECTED_REVISION`, `INVALID_CHECK_DECISION`, `QUANTITY_REQUIRED` (or the existing quantity parser's decimal validation), `INVALID_BACKUP_COUNT`, `INVALID_LEVEL`, `INVALID_PRESENCE`, `INVALID_PACKAGE_COUNT`, `INVALID_BATCH_COUNTS`, and `BATCH_TOTAL_MISMATCH` (400); `HOUSEHOLD_MEMBERSHIP_REQUIRED` (403); `TRIP_NOT_FOUND`, `ITEM_NOT_FOUND`, and `CHECK_ITEM_NOT_FOUND` (404). These messages identify the branch the client should correct or reload.

After checks, the existing `POST /:tripId/suggestions` locks the trip, then selects the previous completed trip and calculates from current stock through the same database transaction before importing its snapshot. A correction holding the trip lock must commit before import can assess stock; a correction arriving after import cannot change that first snapshot. Import records `suggestionsImportedAt` even if no suggestions were available. Check writes never change manual entries or existing suggestions. A draft that already imported suggestions cannot enter this first check flow; re-import returns the saved snapshot. The API also detects pre-migration imported drafts by their suggested entries. No new trip status is introduced.

## Purchase decision

`PATCH /:tripId/entries/:entryId` accepts `{ status, actualQuantity?, expiryDate?, locationId?, destinationTripId? }` while Shopping. Status is `PENDING`, `PURCHASED`, `SKIPPED`, or `MOVED`. For QUANTITY purchases, `locationId` is optional; when supplied it must identify a Location in the URL household and is saved on the entry until Finish. Omission while updating an already purchased entry retains the saved location; explicit `null` or an empty string clears it. Pending, skipped, and moved clear actual quantity, expiry, and entry location. A location on a non-quantity purchase is rejected.

### Move to next trip

`MOVED` is an explicit carryover choice, distinct from `SKIPPED`. A Move request is `{ "status": "MOVED", "destinationTripId": "<draft-trip-id>" }`. The destination must be a different `DRAFT` trip in the same household. The current trip must be `SHOPPING`. The server validates and locks both trips. `GET /:tripId` includes `entries[].moveToTripId` and `entries[].moveToTrip: { id, store, plannedDate, status } | null`. Other entry decisions clear these fields. A repeated identical Move request while Shopping retains one intent; a shopper may switch the entry back to Pending, Skip, or Purchased before Finish.

The client can use the existing household trip list to offer eligible drafts. With one, Move can be one tap; with several, the shopper selects one. No draft is silently created. Move intent remains on the source entry during Shopping; the destination entry appears only after Finish succeeds. A finished source entry cannot be edited.

At Finish, the transaction locks all selected destination trips in ID order and rechecks household ownership and `DRAFT` status before stock writes. Each moved item becomes one `PENDING` entry in its selected draft, with `source: "MANUAL"`, the source priority, and no suggested or actual quantity. If that draft already has a manual or suggested entry for the item, its source, priority, reason, quantity snapshot, and other fields remain unchanged. The existing `(tripId, itemId)` uniqueness and conflict-safe insertion prevent duplicate carryover, including when two source trips target the same draft. A carried entry can be moved again when that later trip enters Shopping. Other drafts and their suggestion snapshots remain untouched. Skip does not trigger this explicit carryover.

Invalid or self destination IDs return HTTP 400 `INVALID_DESTINATION_TRIP`; a destination field on another decision returns HTTP 400 `DESTINATION_NOT_SUPPORTED`; a missing or foreign-household destination returns HTTP 404 `DESTINATION_TRIP_NOT_FOUND`; a destination no longer Draft returns HTTP 409 `DESTINATION_NOT_DRAFT`. A persisted MOVED entry without a destination returns HTTP 409 `MOVE_DESTINATION_REQUIRED` at Finish. If any destination validation or carry write fails, Finish rolls back the destination inserts, purchase restocks, pending-entry updates, and source trip transition together. Repeated/concurrent Finish returns the stored Restocked trip without repeating any of those writes.

| Tracking mode | `PURCHASED` actualQuantity | expiryDate | Finish effect |
| --- | --- | --- | --- |
| QUANTITY | Required positive decimal string, at most six fractional digits | Optional `YYYY-MM-DD` | One stock batch at the resolved location, RESTOCK action, and allocation for the actual quantity |
| FIVE_LEVEL | Required positive integer backup unit count, string or JSON number, at most 2,147,483,647 | Rejected, including an empty string | Increases `backupCount`; `currentLevel` stays unchanged |
| PRESENCE_BACKUP | Same positive integer backup unit count | Rejected, including an empty string | Increases `backupCount`; `isPresent` stays unchanged |

The trip response stores `actualQuantity` as a decimal string for every mode. A nonquantity purchase records an attributable `ADD_BACKUP` state action with actor, timestamp, and before/after state. It creates no stock batch or quantity action. Opening a refill remains a separate explicit inventory state action.

## Finish

`POST /:tripId/finish` atomically moves Shopping to Restocked, marks pending entries skipped, carries moved entries, and applies each purchased entry using its actual amount. Skipped, pending, and moved entries add no stock. For each QUANTITY purchase, location resolves from saved entry `locationId`, item's `preferredRestockLocationId`, then the most recently created located batch for that same item (creation time descending, ID descending). Explicit and preferred locations are validated against the URL household. A valid explicit location becomes the item's preference in the same Finish transaction as its batch and action; an inferred legacy batch location initializes a missing preference. Existing batch locations are never rewritten. The trip row lock serializes Finish; repeated and concurrent calls return the Restocked trip without applying purchases or carryover again. Any validation or write failure rolls back the whole Finish transaction. Quantity purchases continue through InventoryService Restock; backup purchases use InventoryStateService's state mutation boundary.

If a quantity entry has no resolvable location, Finish returns HTTP 400 with `{ "statusCode": 400, "error": "Bad Request", "code": "LOCATION_REQUIRED", "message": "Choose a location before recording this stock.", "itemId": "<inventory-item-id>" }`. No batch, action, preference, entry status, or trip status is committed. The client can save a location on that entry and retry Finish. A supplied location outside the URL household returns HTTP 400 `LOCATION_NOT_FOUND` with the same shape and item ID. Invalid location value types return HTTP 400 `INVALID_LOCATION_ID`. Supplying a non-empty location for a nonquantity purchase returns HTTP 400 `LOCATION_NOT_SUPPORTED` with its item ID. `PATCH` validates supplied locations before saving; Finish validates again.

Invalid amounts or nonquantity expiry return 400. Missing membership returns 403, items or trips outside the household return 404, and invalid trip state returns 409.
