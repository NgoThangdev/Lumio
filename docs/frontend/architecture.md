# Frontend architecture (implemented)

This page describes the active `apps/web/src` entry point as of 2026-10-13. It is an implementation note subordinate to the [master product specification](../specs/master-prompt.md), [Phase 1 scope](../specs/phase-1-scope.md), and approved slices. It does not mark the full Phase 1 experience complete.

The current visual tokens and component conventions are in the [frontend visual foundation](design-system.md).

## Routes and boundaries

`src/main.tsx` mounts the app in `QueryClientProvider`; `src/app/App.tsx` owns `BrowserRouter`, session verification, household selection, and the shared shell. The Vite development server serves the SPA for direct URLs. On a fresh load, `/auth/me` runs before protected routes render; a signed-out visitor is sent to `/sign-in`, with the requested household path retained for sign-in. `HouseholdBoundary` loads memberships and returns an unknown or inaccessible household URL to `/households`.

| Route | Active screen |
| --- | --- |
| `/sign-in` | Sign in or register (`features/auth`) |
| `/households` | List or create households (`features/households`) |
| `/households/:householdId` | Redirect to that household's Home |
| `/households/:householdId/home` | Backend-prioritized Needs Attention and links to Inventory and Shopping |
| `/households/:householdId/inventory` | Search, filters, location/category grouping, assessment, and atomic Add Item |
| `/households/:householdId/inventory/:itemId` | Item stock, assessment, actions, and history |
| `/households/:householdId/locations/:locationId/check` | Full API-ordered, location-scoped stock checklist with Confirm and Correct |
| `/households/:householdId/shopping` | Trips list and trip creation |
| `/households/:householdId/shopping/:tripId` | Draft or active checklist and finished trip |
| `/households/:householdId/shopping/quick-purchase` | Ad-hoc purchase saved directly to Inventory |

`app/` coordinates routing and household context. `features/` contains auth, household, Home, inventory, and shopping screens with their local form state and mutations. `shared/api/` holds the fetch client, response types, and query keys; `shared/ui/` holds small presentation primitives. The older root `src/App.tsx`, `src/ShoppingView.tsx`, and `src/api.ts` are present but are not imported by `main.tsx`. Atomic Design informs component composition; it does not prescribe a folder hierarchy.

## Session and server state

`shared/api/client.ts` sends same-origin `/api` requests with the server-managed, HTTP-only cookie (the Vite dev proxy forwards `/api` to `127.0.0.1:3000`). It parses API `message` errors into `ApiError` with an HTTP status. A 401 outside auth requests dispatches `lumio:session-expired`. On sign-in/register, confirmed sign-out, or session expiry, the app removes all non-session queries and cached mutations before updating the still-observed session query. This clears account-specific data and lets the route guard react immediately. A confirmed sign-out navigates to `/sign-in`; a failed sign-out displays an error and retains the signed-in screen unless the failure itself is a 401 session expiry.

Local API smoke test on 2026-10-11: successful Sign out from Item Detail and Shopping immediately reached `/sign-in`; a signed-out item URL redirected there on reload. An API-offline Sign out kept Item Detail visible with an error. A protected Use request after sign-out in another tab returned 401 and redirected to `/sign-in` without changing stock.

TanStack Query owns session, households, catalog selectors, legacy items, queried Inventory, Home Needs Attention, item detail, stock intelligence, trip list, and trip detail. Keys include household ID, plus item or trip ID where relevant; intelligence also includes the shopping date. Household creation invalidates memberships. Admin catalog creation invalidates its selector. Atomic Add Item invalidates its household's items, Home Needs Attention, intelligence, and catalog selectors; Item Detail then fetches the created item and assessment. Direct Restock, Use, and quantity configuration invalidate item detail, list, Home Needs Attention, and intelligence, which refreshes visible stock, assessment, and activity. Trip changes update the selected trip cache and invalidate the trip list; finishing invalidates the household key prefix, including inventory and intelligence. Forms and purchase drafts remain component state. The API remains authoritative for FEFO, stock totals, assessment, suggestions, permissions, and transaction results.

## UI and current scope

`shared/ui/primitives.tsx` provides `Button`, `Card`, `Notice`, `StockBadge`, and an `ItemVisual` using the shared `Doodle` SVG placeholder over the existing CSS; the shopping screen also uses native buttons and CSS classes directly. `Notice` uses status/alert roles. `index.css` owns the design tokens and responsive styling. Tailwind CSS 4 and its Vite plugin are installed and used for the button `min-h-11` utility, but the app has not converted to a Tailwind component system. No shadcn/ui package or generated shadcn component is integrated; these wrappers are only shadcn/ui-style local primitives. Headless UI is not installed. React 19, React Router 8, TanStack Query 5, Vite 8, and TypeScript 6 are in active use. No PWA manifest, service worker, or offline mutation queue is implemented.

Inventory's Add Item form uses the [atomic Add Item contract](../../apps/api/ADD_ITEM_CONTRACT.md): `GET /households/:id/categories`, `/locations`, and `/tags` return `{ id, name }` selectors; Admins can create options with `POST` and `{ name }`. One `POST /households/:id/items` sends name, primary unit, tracking mode, selected category and location IDs, optional tag IDs, and only that mode's `initialStock`. The returned item `id` opens Item Detail, which refetches stock, batch location, assessment, and activity. Exact quantity `"0"` creates no batch or activity; the selected location remains the item's preference for future quantity writes. Quantity item detail exposes Restock, Use, Admin stock rules, and an Admin-only opening policy. Enabling opening tracking requires an explicit confirmation that one primary unit is one package. Enabled items show server-returned opened/unopened totals and batch opening/effective-expiry dates, with Open and Finish opened actions. Five-level and presence/backup detail expose API-backed level/presence changes and backup additions; Open refill appears only when the item assessment returns `recommendedAction: OPEN_REFILL`. These POST actions refresh item detail, household Inventory, stock intelligence, and Home Needs Attention. Shopping's manual selector includes all three modes per [SHOPPING_CONTRACT.md](../../apps/api/SHOPPING_CONTRACT.md). Quantity purchases accept a positive decimal and optional expiry unless the item has opening tracking enabled, in which case the input guides the shopper to enter whole package counts; backup purchases accept a positive whole number and omit expiry. Finish displays the server result without opening a refill. Inventory and Home use the [read contract](../../apps/api/INVENTORY_READ_CONTRACT.md). Inventory sends supported search, status, category, location, tag, and grouping parameters and renders `{ items, groups? }` with each item's server assessment. Home renders up to four entries in the API order, with `priority`, `action`, `reason`, and `reasons`; links open Item Detail and do not mutate stock. Richer catalog management and PWA/offline behavior remain future work. Quantity stock writes accept a chosen physical location and use backend preference/legacy-batch resolution; see the [location stock-write and Check Location integration note](location-stock-writes.md) for UI behavior and smoke limits.

Check Location is separate from Shopping Trips. Inventory links each household location to the route above. The page renders the API's complete ordered checklist, selected-location stock and batches, status, reason, and saved check time. Confirm and Correct send the response's `stockRevision` as `expectedRevision`; stock changes that produce `STOCK_CHANGED` require a newly reviewed decision. Quantity batch editing appears only after `BATCH_DETAIL_REQUIRED` and uses the API-returned batches. See the [location stock-write and Check Location integration note](location-stock-writes.md) for request details and runtime verification status.

Shopping's **Move to next trip** is a separate checklist decision from Skip. It uses the existing `GET /households/:id/trips` draft list and `PATCH /households/:id/trips/:tripId/entries/:entryId` with `{ status: "MOVED", destinationTripId }`. The source trip response supplies `entries[].moveToTripId` and `entries[].moveToTrip` for saved intent. The FE says the item will move when Finish succeeds; it does not create a destination entry. Other decisions are sent through the same PATCH and clear move intent per the API. `DESTINATION_NOT_DRAFT` refreshes the draft list and waits for a new user choice. Finish invalidates household-scoped queries so source, destination, and related inventory views refetch. The exact contract is in [SHOPPING_CONTRACT.md](../../apps/api/SHOPPING_CONTRACT.md).

Local browser smoke on 2026-10-14 used disposable source/destination trips in `STOCK CHECK FOLLOWUP 2026-10-13`. Skip remained `SKIPPED`; a moved Quantity item displayed its chosen destination and “Will move when this trip is finished.” A destination that already contained that item still showed one entry after Finish. The source finished view retained `MOVED` and said carryover added no stock. A state-mode item was moved, then changed to Purchased before Finish; the UI returned it to `PURCHASED` with no saved-move note, and Finish showed a backup purchase only. Raw HTTP payloads/responses were not captured in DevTools, so the API evidence here is the successful API-backed response shown by the app and the refetched trip snapshots. Repeated Finish and `DESTINATION_NOT_DRAFT` race handling were not observed in this browser pass.

## Quick Purchase

Quick Purchase is separate from Shopping Trips and is linked from the Shopping screens. It searches the legacy household item list and loads the selected item's detail before enabling a purchase. QUANTITY uses `POST /items/:itemId/restock` with `quantity` and optional `expiryDate`; opening-enabled items require a whole package amount based on the returned `openedTrackingEnabled`. FIVE_LEVEL and PRESENCE_BACKUP both use `POST /items/:itemId/state/backups` with integer `count`, leaving current level or presence unchanged. Expiry is only sent for QUANTITY.

“Add as a new item” navigates to the Inventory atomic Add Item form carrying the search name and quantity draft; optional quantity expiry is entered in that form. The form submits its existing single `POST /items` request with selected category/location and mode-specific `initialStock`; it does not Restock afterward. If the user selects a nonquantity mode, the form requires their initial level/presence and backup count instead of deriving them from the purchase amount.

Quick Purchase refreshes the selected item, household item/Inventory, Home Needs Attention and stock intelligence query families. A successful stock mutation remains reported as saved if refresh fails, with a warning. HTTP 4xx responses other than 408 are shown as confirmed rejections; network errors, HTTP 408 and HTTP 5xx outcomes are treated as uncertain, preserving the entered draft and advising the user to check Inventory/Item Detail activity before retrying. The mutation is called once and is not automatically retried.

Browser smoke on 2026-10-12 used the disposable local account and household recorded in the following Opened Quantity smoke note. FIVE_LEVEL accepted 2 backups and retained Full (2 → 4); PRESENCE_BACKUP accepted 2 and retained Present (1 → 3). The no-match path carried the product name and 2.5 quantity into Add Item; one atomic create produced a located 2.5 bottle batch and exactly one `Initial stock` activity entry, then opened Item Detail. The existing Shopping Trip list still showed its prior single finished trip; Quick Purchase created no trip. ## Phase 1 Undo integration — 2026-10-13
