## Goal

Improve the frontend's readability, ownership, and maintainability through small, reviewable refactors. Preserve working user flows while reorganizing components, stateful logic, data access, and styles. Performance changes require a measured problem and a separate justification.

This file is a temporary execution guide, not a product specification. Read it before each refactor task. It does not authorize implementing the entire plan, adding dependencies, or changing product behavior. Execute only the task assigned by the user.

## Constraints

- Inspect `git status` and relevant diffs before editing. Preserve all pre-existing staged, unstaged, and concurrent changes. Do not stage or commit unless requested.
- Edit only the assigned FE scope and relevant FE documentation. Do not modify `apps/api`, schema, migrations, product specifications, or root dependencies/lockfiles without explicit authorization.
- Preserve visible behavior, routes, payloads, API result interpretation, permissions, locale strings, accessibility, and mobile/light/dark presentation.
- Preserve query key values, household/user scoping, invalidation effects, retry behavior, and mutation error semantics during structural extraction. Changes to those behaviors need explicit justification and approval in the task.
- Preserve the distinction between rejected mutations, uncertain mutation outcomes, and saved mutations whose follow-up refresh failed. Never introduce automatic retry of stock writes.
- Do not implement business rules in FE utilities or hooks. UI input validation and presentation mappings must continue to follow the actual contract.
- Avoid adding a state manager, UI library, test framework, or architecture boilerplate as part of file extraction. Propose dependency changes separately.
- If a requirement, contract, ownership boundary, or observed behavior is ambiguous, record the exact question and ask the user before the dependent change. Continue independent authorized work where possible.
- Record existing bugs separately. A refactor is not implicit authorization to redesign behavior or repair a contract. Provide reproduction/evidence and ask before expanding scope.

## Organization conventions

| Area                 | Responsibility                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| `app`                | Application initialization, route composition, session/household boundaries, shell                 |
| `features/<feature>` | Pages, sections, forms, interaction logic, and feature-specific data access                        |
| `shared/api`         | HTTP transport/errors, shared response contracts, query keys and genuinely shared data integration |
| `shared/ui`          | Reusable presentation components and illustrations/icons                                           |
| `shared/i18n`        | Static EN/VI JSON, formatting, enum/descriptor translation                                         |
| Shared styles        | Tokens, themes, base styles, shared controls/layout                                                |
| Feature styles       | Styles owned by that feature, extracted only with cascade verification                             |

- Keep related code close together. Do not create empty `hooks`, `utils`, `libs`, or `constants` folders in every feature.
- Extract components around a coherent UI responsibility. A page may retain queries or local state when doing so keeps ownership clear.
- Extract a custom hook for a coherent stateful process; use a descriptive `use...` name. Do not move an entire large page into a single equally large hook.
- Use ordinary functions for pure formatting/transformation. Give files and exports specific names rather than a global miscellaneous `functions.ts` or `utils.ts`.
- Keep feature-only types/constants beside their consumers. Shared API types can remain shared when multiple features consume the same contract. Avoid duplicating DTOs or forcing every type into a feature.
- Query options may colocate a query key and query function when useful. Do not wrap every query merely to add another layer.
- Extract shared behavior only after verifying that the semantics really match. Similar-looking invalidation blocks may have different refresh/error requirements.
- Shared modules must not depend on feature pages or app composition. Avoid circular imports and unnecessary barrel files.
- Import paths: use relative imports (`./`, `../`) within a feature. For imports across `app`, `features`, and `shared`, use `@/` rooted at `apps/web/src` once the alias is configured in both TypeScript and Vite. Do not use absolute filesystem paths in source imports. Apply the alias incrementally in the assigned task scope; do not rewrite existing imports solely to change their style. No dependency is needed for this convention.
- Existing exception: features import `app/useHousehold.ts`. Preserve this until the explicit context-boundary task resolves ownership; do not claim strict downward dependencies already exist.
- No arbitrary line-count limit. Evaluate responsibility, coupling, readability, and the cost of reviewing a change.
- Preserve React component identity, keys, mount timing, focus, and form drafts when moving JSX. Review effects carefully; moving code alone must not reset input or stale-review state.
- Keep CSS selectors and import order stable during initial extraction. Changing specificity, cascade, responsive behavior, or theming belongs in a separately reviewed change.

## Per-task workflow and Definition of Done

1. Frame the task as Goal / Context / Constraints / Definition of Done. Record the assigned step and exact scope.
2. Inspect current code and worktree; do not rely on this guide's historical line counts or prior smoke reports.
3. Identify state owners, query keys, request/response shapes, mutation side effects, and UI behavior that extraction must preserve.
4. Make focused changes. Prefer structural extraction before changing state synchronization or abstractions.
5. Run web build, lint, touched-file formatting checks, and scoped diff checks. Include new untracked files in review. Report pre-existing warnings separately and do not broadly format unrelated files.
6. Browser-smoke affected behavior using a disposable household for mutations. Do not modify demo data. Check 320/390 CSS px, light/dark and EN/VI for moved UI; report unavailable checks honestly.
7. For mutation refactors, compare important requests/results and resulting screens. Log only sanitized evidence; never record credentials, cookies, tokens, invitation secrets or subscription secrets. Remove temporary instrumentation without overwriting concurrent edits.
8. Verify relevant draft preservation, loading/empty/error states, role gates, reload/navigation, and refresh behavior. Build success is not browser-flow success.
9. Report changed paths, responsibility changes, checks actually run, observed behavior, existing issues and remaining unverified branches. Update relevant FE documentation when ownership changes.
10. Stop at the assigned step. Do not automatically execute the next step.

At planning time, `apps/web/package.json` has no test script and no FE test files were found in the inspected scope. Do not claim automated regression coverage exists. If a meaningful automated check needs a new framework/dependency, propose that separately; do not add it silently.
